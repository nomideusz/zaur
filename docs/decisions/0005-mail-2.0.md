# ADR-0005: Zaur Mail 2.0, a clean-room webmail rebuild

## Status

Accepted

## Date

2026-09-12

## Context

`apps/webmail` has accumulated years of layered features, entangled session/auth server code,
and UI that has drifted far from any design system. A full redesign prototype (shell and compose
panel handoff: light theme only, Libre Franklin, plum accent, cards, cozy density) now defines the
target look, but the prototype intentionally excludes async states, dark mode, and mobile
behavior — those gaps belong to implementation.

Two developments make a fresh start cheaper than a gradual facelift:

- Zaur Mail is becoming a workspace. Files and Zaur Meet will share the same shell and design
  language (designs to follow). Getting the shell, tokens, and session plumbing right once, in a
  clean app, sets their baseline.
- SvelteKit's experimental remote functions (`query`, `command`, `query.live`) and the async
  compiler are already exercised in webmail 1.0 (`unread.remote.ts`, `settings.remote.ts`), so the
  risk of the pre-release API is known and accepted.

The production client must stay stable throughout; the rebuild cannot put it at risk.

## Decision

Build Zaur Mail 2.0 as a new SvelteKit application, `apps/mail2` (`@zaur/mail2`), implementing
the redesign from scratch rather than refactoring webmail in place. Webmail 1.0 remains the
production client, frozen to bugfixes, until the cutover checklist passes.

### Scope

- Light theme only for now; the token set in `apps/mail2/src/routes/styles/tokens.css` defines a
  single light palette. Dark mode is deferred, not designed.
- Files and Zaur Meet are out of scope. The shell and routing leave room for sibling surfaces but
  nothing is built until their designs land.
- Reuse, don't fork, the mail stack. Shared logic lives in workspace packages, not in the app:

```text
apps/mail2
  src/lib/server/*.remote.ts   query / command / query.live — the client↔server boundary
    ├── @zaur/server-auth      sessions, OAuth, Stalwart auth (extracted from webmail)
    ├── @zaur/mail-core        JMAP client, mapping, sync, outbox (shared with webmail)
    └── @zaur/ui, @zaur/sprite design system pieces
```

- Remote functions replace webmail's ad-hoc `/api/*` endpoints and fetch wrappers as the primary
  data boundary. Where JMAP proxying or SSE push must stay server-mediated, the 1.0 patterns
  carry over behind remote functions.
- Compose keeps the durable offline outbox from 1.0: pending writes live in the local database
  and drain when connectivity returns.
- UI is Ark UI Svelte + Tailwind v4, driven by the token set; the prototype's resolved variants
  (accent, type, density, card treatment, 520px list, `33em` measure) live there as tokens.

### Session sharing

2.0 shares 1.0's login instead of building its own auth. This requires:

- an identical `SESSION_SECRET` for both apps,
- both apps pointing `STORE_DB_PATH` at the same SQLite session store,
- `SESSION_COOKIE_DOMAIN` (e.g. `.zaur.app`) so the session cookie is shared across sibling
  subdomains in production. In development, cookies are not port-scoped, so localhost instances
  share sessions without configuration.

`SESSION_COOKIE_DOMAIN` is new; webmail 1.0 and mail2 both read it through `@zaur/server-auth`.

### Cutover checklist

2.0 replaces 1.0 only when it reaches parity on:

1. Send and receive, including attachments, drafts, and folder management.
2. Offline drafts and the outbox.
3. Web Push.
4. Search.
5. Multi-account.
6. PWA installability.

Phone pass and mail2-specific login/OIDC are explicitly post-cutover work.

## Alternatives considered

### Refactor webmail in place

Keeps one client, but destabilizes the production app for months and forces every redesign change
through the existing messy structure. Rejected.

### Ship the redesign behind feature flags in webmail

Avoids a second app, but doubles the CSS/theme surface in the codebase we are trying to shrink,
and the flags would linger indefinitely. Rejected.

### Fork webmail and prune

A fork inherits the architecture and entanglements; archaeology on 1.0 costs more than extracting
the genuinely shared code into packages and starting the UI clean. Rejected.

### Wait for remote functions to stabilize

The API surface is small, 1.0 already depends on it, and plain `+server.ts` endpoints remain
available as an escape hatch if a pre-release change breaks something. Rejected; versions are
pinned per app so 1.0 is never forced to upgrade.

## Consequences

- Two SvelteKit mail apps coexist in the monorepo during the transition; the workspace packages
  (`@zaur/server-auth`, `@zaur/mail-core`) are the compatibility surface between them.
- Session-store and cookie configuration become shared infrastructure: `SESSION_SECRET`,
  `STORE_DB_PATH`, and `SESSION_COOKIE_DOMAIN` must be provisioned for both apps.
- `@zaur/server-auth` must stay framework-agnostic (`process.env`, no `$env/*`) so it works under
  `node --test` and can serve future non-SvelteKit services.
- mail2 tracks the SvelteKit 3 pre-release line (pinned `3.0.0-next.x` with the matching
  `adapter-node` `6.0.0-next.x`); upgrades may involve churn, isolated to 2.0. In Kit 3 all app
  config lives in `vite.config.ts` (`sveltekit({...})`), `$lib` is replaced by `#lib` subpath
  imports, and remote functions remain behind `experimental.remoteFunctions`.
- Design decisions made here (tokens, shell, density) become the baseline for Files and Zaur Meet.
- Two clients mean some fixes are paid twice; keeping 1.0 frozen to bugfixes bounds this cost.

## Delivery sequence

1. Foundation: extract `@zaur/server-auth`, scaffold `apps/mail2`, tokens, shared session
   (`whoami`) — done.
2. Read path: mailboxes → thread list → reader over JMAP via remote queries.
3. Compose path: floating compose panel and dock, drafts, offline outbox.
4. Live updates: SSE-backed `query.live`, unread badges, Web Push.
5. Search, settings, multi-account.
6. PWA hardening and cutover per the checklist.
